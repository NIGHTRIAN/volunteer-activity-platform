# A2 阶段：管理端页面

对应方案：§4（管理端功能）、§6（判定与防脱岗）、§7（权限）、§8（展示层级）。

产出：活动详情（工作台）· 现场看板 · 名单与导入 · 签到复核 · 考勤汇总 · 导出。

---

## 一、结构：为什么是"列表 → 详情 → 功能页"三层

管理端的功能是**围绕一个活动**展开的。如果把看板、名单、考勤、导出
平铺在活动列表上，每行要塞五六个按钮，列表会变得无法扫读。

因此：

```
活动列表 → 活动详情（工作台） → 现场看板 / 名单 / 考勤汇总 / 导出
```

详情页只负责回答"**这个活动现在什么状态、我能做什么**"。

## 二、现场看板（`board_page.dart`）

### 2.1 设计目标只有一个

让人**站在活动现场、一手拿手机、一眼看出**"谁到了、谁没到、谁需要我处理"。

因此：
* 四个数字放最上方、字号最大（已签到 / 待确认 / 尚未签到 / 已移出）；
* 「待确认」是**唯一需要行动**的类别，用警示色并可点进复核；
* 点任一计数即筛选名单，再点一次取消（比强制去找"清除筛选"顺手）。

### 2.2 两条不能含糊的计数规则

**规则 1：`有效名单 = 已签到 + 待确认 + 尚未签到`**

「已移出」单独计一个数，**不混进未签到**。混进去会：
* 冤枉已经退出的人；
* 让到场率凭空变低。

已移出的人不参与筛选——他不在有效名单里。

**规则 2：到场率把「待确认」算作到场**

`pending_review` 是"证据不足待核实"，不是"没来"。算作缺席等于
在核实之前就下了结论。

### 2.3 前台轮询，但不做判定

每 20 秒静默刷新一次；**切回前台立刻刷一次**（用户切回来最想看的是"现在"）。
静默的含义是失败**不打断界面**——现场一块正在被人看的看板，
因一次网络抖动变成错误页，会让人以为活动出问题了。

方案 §6.2 明确"App 不承担任何定时判定"。客户端只显示，
超时结算完全在服务端。

### 2.4 免责声明与留存期

免责声明**由服务端下发**（`board.disclaimer`），不在客户端硬编码：
它是发布者面对"你为什么扣我时长"这类质疑时的依据，
措辞必须与服务端记录的口径一致。客户端自己写一份，两边就可能对不上。

留存期提醒（"数据将于 X 后不可访问，请在此之前完成导出"）必须在
**数据还在的时候**说，而不是等销毁之后。

## 三、签到复核（`checkin_review_page.dart`）

### 3.1 这一页决定了"防脱岗"是帮人还是冤枉人

方案 §13-A5 自己就承认了「『通知没到』会被记成『人不在』」。
复核页就是修正误判的地方。因此它的原则是：**把证据摊开，判断交给人**。

* 显示**评分构成**（哪些项得分、哪些没得），而不是只给总分——
  发布者据此能判断"没得分"是可疑还是正常；
* **距离与精度并排显示**：室内 ±80m 时，一条"距签到点 120 米"的记录
  完全可能是本人。只看距离就驳回，是这一页最容易犯的错；
* **驳回必须填备注**（服务端强制，页面也本地先拦一次），
  因为志愿者会看到这条说明——不解释就驳回，他不知道自己哪里做错了。

### 3.2 已定案的记录不给复核入口

只有 `pending_review` 可复核。已通过的记录界面明确说明"已定案"，
并指向正确的路径（人工补录 / 联系管理员），而不是给一个点了必然失败的按钮。

## 四、名单与导入（`roster_page.dart`）

### 4.1 录入与发码刻意分成两个动作

它们的**后果完全不同**：
* 录入名单 → 只是数据，录错改一下就行；
* 发邀请码 → **一次性的**，发出去就消耗掉了。

因此邀请码明文**只显示一次**（服务端不下发第二次），
界面上有独立的高亮卡片、"我已记下"、逐条复制。

文案明确要求"逐条私下发给本人"——贴到群里等于把码公开，
任何人都能拿它去绑定别人。

### 4.2 导入必须能"粘贴"

发布者手上的名单来自报名表（Excel / 问卷导出），他做的最自然的事是
**从表格里复制一片单元格然后粘贴进来**。因此不做"一行一行加"，
而是一个多行文本框，宽容解析制表符 / 逗号 / 中文逗号 / 分号。

宽容解析是刻意的：让发布者为"分隔符不对"返工是不合理的，
真正的校验（学号格式、重名）由服务端做。

### 4.3 逐行报告必须摊开

批量导入最常见的失败不是"全错"，而是**几十行里错了三行**。
只报"导入完成"的话，发布者不知道哪三行有问题——而这三个人
第二天就签不上到。

导入报告因此列出：第几行、学号、**具体原因**，并说明
"修正后可以只重传这些行"（同一学号视为更新，不会重复）。

## 五、考勤汇总（`activity_page.dart` 内）

### 5.1 措辞比数据更重要

汇总会被人当作"谁干得好、谁在摸鱼"的依据。因此：

* 免责声明放在**最上方**，不是页脚；
* 分类计数把「证据不足」与「缺席」**分开列**；
* 每行直接给出**完成率百分比**，而不是只给一个等级——
  决策 D-7 的判据是"完成率 ≥0.7 记 partial"，只给标签的话，
  读的人无法判断"这个 partial 到底是差一点还是差很多"。

### 5.2 一个容易忽略的区分

`attendanceRate` 为 `null`（无已定案任务）与 `0%`（确实一次都没完成）
**必须分开呈现**。前者在界面上显示"尚无已定案的抽查"，
后者才显示"完成率 0%"。

把 `null` 显示成 0% 会被读成"一次都没完成"，而实际含义是
"还没有可判定的事"（抽查尚未发生）。

## 六、状态流转（`:transition`）

### 6.1 `from` 是乐观锁

请求必须带上客户端认知的 `from`。服务端在状态已被别人改过时返回
`40901`，而不是把一次基于过期认知的流转硬写进去。

### 6.2 客户端先过滤按钮，但不做判定

界面按与服务端一致的合法流转表（方案 §5.1）决定显示哪个按钮，
只是为了**让用户看不到点了必然失败的按钮**——判定仍在服务端。

### 6.3 取消要二次确认 + 原因

取消**不可撤销**，原因会记录在活动里（服务端强制 ≥5 字，
页面在按钮禁用前就给出实时字数提示）。
对话框明确说明"未发生的抽查会被豁免，不影响到场者的记录"。

## 七、导出（`GET /activities/{id}/export`）

导出是**直接下载**（网页方案 §6.4.8），不是"建任务 → 轮询"。

移动端的处理方式：把 URL 与用法展示出来（可选中复制），
而不是假装能"帮用户下载"。因为用户拿到 CSV 之后真正需要的是
**把它发到自己的电脑或邮箱**——那是系统的事，App 没有权限静默完成。

同时说明默认脱敏，以及"需要完整手机号时在电脑端显式勾选，
那次导出会进敏感导出审计"（决策 D-3）。

## 八、本轮修复的契约不一致（都是实测发现的）

| # | 问题 | 症状 | 根因 |
|---|---|---|---|
| 1 | `checkinStatus` 两套词表 | **看板上所有已签到的参与者都显示"未知状态"** | 服务端下发 `success`/`none`，客户端 enum 期望 `checked_in`/`not_checked_in` |
| 2 | `method` 写入值不统一 | 线上长期并存 `gps` 与 `geo` | 种子与早期提交写 `gps`，契约要求 `geo` |
| 3 | `ActivityBoard` 少两个字段 | 免责声明与留存期提醒取不到 | 模型没有 `disclaimer` / `dataDestroyAt` |

**处置**：
* 服务端与客户端**统一取 `checkin.status` 原值**（`success` / `pending_review` / `none`），
  不再引入翻译层；解析层仍兼容旧写法，避免历史数据变"未知"；
* 写入侧统一用 `geo`（读取侧兼容 `gps`）；
* 补齐模型字段。

**并加了三条守卫测试**（`mock_server/test/smoke.js`）：
* 名单行 `checkinStatus` 必须与 `checkin.status` 同一词表，
  且明确排除 `checked_in` / `not_checked_in`；
* 无记录时必须是 `none`，且四态之和等于有效名单人数；
* 写入侧 `method` 一律是 `geo`。

这类"两套词表并存"的 bug 特别值得警惕：**它不会报错，只会让界面
安静地显示错的东西**，而那一列恰好是发布者现场最依赖的。
