## 三、设计决策中我做的取值（可能与你预期不同）

### ⚠️ D-1　末次抽查留白：**30 分钟**，不是 15 分钟

| | |
|---|---|
| **冲突** | 方案 §6.2 同时给了两条约束：<br>(a)「末次不晚于 `endTime − 15min`」<br>(b)「2 小时活动 3 次（T+15 / T+45 / T+75）」<br>留白取 15 → 可用区间 `[15, 105]` → 30 分钟间隔产出 **4 次**（T+15/45/75/105），与 (b) 矛盾<br>留白取 30 → 可用区间 `[15, 90]` → 恰好 **3 次** ✅ |
| **我的取值** | **30 分钟**（`ATTENDANCE_LAST_TASK_MARGIN_MIN = 30`） |
| **依据** | 验收 A20 是**可判定**的断言，(a) 是描述性表述。冲突时以可判定的为准 |
| **影响** | 2 小时活动：3 次；3 小时活动：4 次（T+15/45/75/105）；1.5 小时活动：1 次（T+15） |
| **★ 需你确认** | 若正确值是 15 分钟，那么「2 小时 3 次」这个说法需要改成 4 次，**验收 A20 也要改**。请后端明确以哪条为准 |

### ~~D-2　动态签到码的判定口径~~ → **已决：不启用该功能**

见 `docs/decisions.md` D-2。方案 §6.3 的动态签到码**整体不实现**，

### D-3　重复签到：**幂等返回**，不是报错

| | |
|---|---|
| **我的取值** | 同一活动同一用户重复提交，返回已有记录 + `alreadyCheckedIn: true`，**不报 `30004`** |
| **理由** | 志愿者重复点「签到」是现场最常见的操作（网络慢时会连点）。报错会让他以为失败，继续点 |
| **若不同** | 改为返回 `30004` |

### ⚠️ D-4　「活动内重复」的精确语义（导入接口）

这是我在实现中**改过两次**的地方，因为它直接决定发布者会不会误以为导入成功。

| 场景 | 我的行为 |
|---|---|
| 学号已存在，且这行**不带来新信息**（姓名一致、手机号一致或未填） | ❌ 拒绝，报「名单中已存在该学号」 |
| 学号已存在，但**补齐了库里缺失的手机号后四位** | ✅ 接受，更新该记录 |
| 学号已存在，姓名不同**但**手机号后四位一致 | ✅ 接受（同一人改名或录入笔误） |
| 学号已存在，姓名与手机号后四位**都对不上** | ⚠️ 标「待确认」，**且一个字段都不写**，保留原值 |
| 学号不存在 | ✅ 新增 |

**为什么"待确认"不写任何字段**：这一行的姓名和手机号都已与库里矛盾，任何一个值都可能是错的。
照写等于「用户的错数据静默覆盖发布者手里的对数据」，而发布者以为自己只是"标了个待确认"。
保留原值，等他核对完再改。

**★ 需你确认**：这四个分支是否符合《接口契约》对导入的预期。

### ⚠️ D-5　在岗抽查的判定范围比签到宽松

| | |
|---|---|

| | |

## 五、我无法从文档确定、需要业务决策的点

1. **管理端邀请码 `1111` 与「三条零成本底线」冲突**（详见 `docs/open-issues-app.md` O-1）。
   我已按 §2/§14.1/A2 实现（默认 `1111`、服务端可配置、不强制更换）。
   但 README §3.3 底线①写的是「管理端不使用固定默认邀请码」。**这两处必须有一处改**。

2. **导出是否需要完整手机号**（见 D-6）。

3. **活动「已发布」与「进行中」的切换由谁触发**：
   方案 §4.4 说「开始：一键（到点也可自动）」。我的实现是必须**显式点开始**，
   不会自动流转。若要自动流转，需要服务端定时任务，且要注意
   「自动开始」在管理端不在线时的行为。

4. **`enrolled` 的语义**：是"名单人数"还是"报名人数"？方案 §3 列为活动字段，
   §1.3 又说「用户端自助报名」在范围外。我取的是**有效名单人数**。

5. **`quota` 超出时的行为**：用户端没有自助报名，那 `quota` 只影响名单导入。
   超出时我是**拒绝该行并报 `30008`**，而不是允许超员。

6. **被移出名单的人能否重新绑定/签到**：
   我的实现是「移出后清理设备绑定不允许重新绑定，直到发布者把他重新加回名单」。
