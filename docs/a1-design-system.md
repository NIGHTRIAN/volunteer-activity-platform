## 一、设计系统的两条硬规则

### 规则 1：状态文案与颜色只有一个来源

`packages/shared_ui/lib/src/status_visuals.dart` 是**唯一**把领域状态映射到
界面表现的地方。页面里不允许出现：

```dart
// ❌ 禁止
color: status == 'success' ? Colors.green : Colors.orange,
text:  status == 'pending_review' ? '待确认' : '已通过',
```

理由：同一份状态会出现在用户端、管理端、将来的网页端。
各写一份的结果是"用户端说『已签到』是绿的，管理端是蓝的"，
而这类不一致在**争议场景**下会变成"到底以哪个为准"的扯皮。

### 规则 2：不给未发生的事加处罚色彩

这是本项目在视觉上最容易犯错、后果也最严重的地方：

| 状态 | 用色 | 理由 |
|---|---|---|
| 在岗 `pending_review` | warning（黄） | 是"需要人看一眼"，不是错误。画成红色会让志愿者以为自己被罚了 |
| 考勤 `partial` / `insufficient` | warning | 完成率不足**不定性为缺席**（方案 §6.4.7） |
| 考勤 `absent` | danger | 确实没到场 |
| 名单 `not_checked_in` | danger | **不用中性灰**：活动进行中这是需要行动的状态，灰色会被忽略 |

`design_system_test.dart` 里有对应的断言，包括：

* 在岗「已超时」的说明文案**必须**包含"不自动扣减"（方案 §4.8）；
* 「证据不足」不得用 danger 色。

## 二、主题：为什么两端共用一套、只在密度上分叉

```dart
AppTheme.build()                // 用户端：一屏一事，留白充足
AppTheme.build(compact: true)   // 管理端：信息密集，行高与内边距收紧
```

**不分成两套主题**：分成两套意味着颜色、圆角、状态色都要维护两份，
迟早出现两端不一致。只把"垂直节奏"参数化，其余全部共用。

### 三个刻意的取舍

**1. 用描边而不是阴影划分层次。**
阴影在廉价屏上容易糊成灰块，而户外强光下几乎看不见。
1px 描边在任何条件下都可靠。

**2. 不打包中文字体。**
一个思源黑体子集动辄 3～8MB，而本 App 的目标是"扫码即下"。
依赖系统字体（Android 上落到 Noto Sans CJK，各厂商 ROM 都内置）。
代价是字形随 ROM 略有差异，可以接受。

**3. 中文行高给到 1.55。**
中文没有西文的 x-height 缓冲，行距过密会显著降低可读性——
管理端的名单与考勤明细尤其明显。

## 三、踩到的两个 Flutter 坑（都已在代码里注明）

### 坑 1：`Size.fromHeight` 会把整个 ButtonStyle 弄失效

```dart
// ❌ 看起来没问题，实际会让主题里的按钮样式被静默忽略
FilledButton.styleFrom(minimumSize: const Size.fromHeight(52))
```

`Size.fromHeight(52)` 实际是 `Size(double.infinity, 52)`。
`ButtonStyleButton` 在合并默认样式时要求尺寸有限，于是**整个
ButtonStyle 被判定非法并退回 Material 默认**（最小高度 40）。
症状是"主题里明明写了 52，按钮却是 40 高"，**且不报任何错**。

### 坑 2：`visualDensity` 是在 `minimumSize` **之后**减掉的

```
最终高度 = max(minimumSize.height - density.vertical * 4, 0)
```

管理端主题开了 `VisualDensity.compact`（vertical = −2），于是
"写 52"实际渲染成 **44**；"写 44"（无障碍下限）渲染成 **36**。

阴险之处：读 `theme.filledButtonTheme.style.minimumSize` 仍然显示 52，
**只有真的量渲染尺寸才能发现**。`AppTheme._minHeightFor` 做了补偿，
`admin_app/test/widget_test.dart` 里有量尺寸的断言守着。

## 四、异步状态的表示：为什么不用 `FutureBuilder`

页面需要的状态比 `FutureBuilder` 多一样：**"有数据但要重新加载"**。

* 管理端看板是**前台轮询**的（方案 §6.2 不启用推送）；
* 用户端列表下拉刷新时也希望保留旧数据。

如果刷新时先清空再加载，界面每次都会闪一下骨架屏——
现场用起来很糟，而且会让人以为数据丢了。

因此 `AppResult<T>` 的三个状态**都带 `previous`**：

| 状态 | 有旧值时界面应显示 |
|---|---|
| `loading(previous:)` | 继续显示旧数据（不闪骨架屏） |
| `failure(error, previous:)` | 继续显示旧数据 + 顶部一行"刷新失败"提示 |
| 首次加载失败（无 previous） | 整页错误 + 重试按钮 |

`AppController` 另外做了三件事：

* **并发保护**：同刻只允许一个在途请求，重复调用直接返回；
* **静默刷新**：前台轮询失败时**保留原状态、不暴露错误**——
  一次网络抖动不该把正在看的看板换成错误页；
* **`mounted` 保护**：销毁后不 `notifyListeners()`，避免
  "setState called after dispose"。

## 五、权限（方案 §7）

### 用户端申请

| 权限 | 用途 |
|---|---|
| `INTERNET` / `ACCESS_NETWORK_STATE` | 与服务端通信、判断在线状态 |
| `ACCESS_WIFI_STATE` | 读 Wi-Fi BSSID 作为**加分辅证** |
| `ACCESS_FINE_LOCATION` | 签到围栏主判据 |
| `ACCESS_COARSE_LOCATION` | 让 Android 12+ 出现"大致位置"选项，避免用户只剩"拒绝" |

### 刻意不申请

| 权限 | 不申请的理由 |
|---|---|
| `ACCESS_BACKGROUND_LOCATION` | 方案 §7 明确"只按需采集，不做持续轨迹"。后台定位是最容易被拒绝、最容易被质疑的一类权限，而签到与在岗确认都是**前台**动作 |
| `READ_PHONE_STATE` / `READ_CONTACTS` / `CAMERA` / 相册 | 与本项目无关。权限越少，用户信任成本越低 |

### 管理端**不申请定位**——但需要一个显式移除

管理端的职责是发布活动、看名单、现场点名；**位置判定的主体是志愿者**：

* `POST /activities/{id}/checkins`（签到）与
  `POST /attendances/{taskId}:confirm`（在岗确认）都要求**志愿者本人**
  携带定位证据（验收 A19：仅点按「我在」而无现场证据不得通过）；
* 发布者对这些记录只做**复核**（通过 / 驳回），复核是纯管理端动作。

**但这里有一个实测踩到的坑**：管理端依赖 `shared_platform`，
而它引用了 `geolocator`。插件的 `AndroidManifest` 声明了
`ACCESS_FINE_LOCATION` / `ACCESS_COARSE_LOCATION`，
**清单合并**会把它们并进管理端 APK。

后果不是"多一行声明"，而是：用户首次启动管理端时，
系统会**弹出定位权限请求，而管理端永远用不到它**。
这会直接损害"权限最小化"这条底线的可信度——用户一旦发现一次
无关的权限索取，后面所有隐私说明都会被怀疑。

处置：在管理端清单里用 `tools:node="remove"` 在合并后剔除这两项。

```xml
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION"
    tools:node="remove" />
<uses-permission android:name="android.permission.ACCESS_COARSE_LOCATION"
    tools:node="remove" />
```

**构建产物已用 `aapt2 dump permissions` 校验**（见下）。

### 构建产物的实际权限（实测）

| 权限 | 用户端 | 管理端 |
|---|---|---|
| `INTERNET` | ✅ | ✅ |
| `ACCESS_NETWORK_STATE` | ✅ | ✅ |
| `ACCESS_WIFI_STATE` | ✅ | ✅ |
| `ACCESS_FINE_LOCATION` | ✅ | ❌ 已移除 |
| `ACCESS_COARSE_LOCATION` | ✅ | ❌ 已移除 |
| `ACCESS_BACKGROUND_LOCATION` | ❌ | ❌ |

后台定位在两端都**不存在**——这是方案 §7「只按需采集，不做持续轨迹」
在构建产物层面的证据。

### 明文 HTTP 的处置

开发期 Mock 跑在 `http://10.0.2.2:8080`，而 Android 9+ 默认禁止明文 HTTP。
不配置的话所有请求都会失败，且错误信息与"网络不通"完全一样。

因此加了 `network_security_config.xml`，但**只放开**
`10.0.2.2` / `127.0.0.1` / `localhost` 这几段，
`base-config` 仍是 `cleartextTrafficPermitted="false"`。
这样公网域名依旧强制 HTTPS——否则它会在上线后变成一个静默的降级通道。

## 六、依赖注入：为什么手写而不用 get_it / provider

要注入的服务是**固定的一小组**（API 客户端、令牌存储、设备指纹、
网络状态、定位、离线队列、时钟），且两端结构相同。手写容器带来：

* 零外部依赖（方案 §1.3 要求开发环境可复现）；
* 编译期就能发现"忘了注入某个服务"；
* 测试里可整体替换（`AppServices` 不可变）。

`AppScope.of(context)` 在找不到时**抛断言而不是返回 null**：
忘记包 `AppScope` 是接线错误，应该在开发期立刻炸掉。

`AppServices.selfCheck()` 在 `main()` 里调一次，把配置问题
（例如 `API_BASE_URL` 少了 `/api` 前缀）在**启动期**就暴露，
而不是等用户点到某个页面才失败。

## 七、启动流程：为什么恢复授权不放在 `main()` 里 `await`

恢复授权要读系统密钥库，这是异步且**可能失败**的
（密钥库不可用、系统升级后密钥失效）。如果在 `main()` 里 await，
失败时屏幕上什么都没有——用户看到一个永远白屏的 App，
既不知道发生了什么，也无法自救。

放在组件树里（`ServiceRoot` 的 `FutureBuilder`），就至少能显示
"正在恢复登录状态…"以及失败原因与重试按钮。

两条刻意的处理：

1. **授权过期一律当作未登录**。不要显示"已登录但什么都点不动"的主页——
   用户面对处处报错的主页，比面对绑定页更难理解。
2. **设备指纹不符就清掉授权并说明原因**。换手机后必须重新绑定
   （方案 §5.2 把授权绑到设备上）。不主动清理的话，
   每次请求都会拿 40301，而用户完全不知道自己该做什么。

## 八、A3 用户端页面

用户端主界面是三个底部标签：**活动 / 在岗 / 记录**。

用底部标签而不是把所有内容堆成一个长页面，是因为**在岗抽查有时间压力**
（响应窗口只有几分钟），必须让用户一步到位；而"记录"是低频查看的，
不该占据首屏。

### 8.1 绑定页（`bind_page.dart`）

`POST /auth/bind` `{ activityId, userNo, inviteCode, name?, phoneSuffix?, deviceId }`

**二次校验字段做成选填。** 服务端的实现是：两项都不提供时**跳过**校验，
提供了才比对，都不匹配才拒绝。因此界面把它们标为"选填"：

* 填了 → 服务端核对，不匹配当场拒绝（能阻止冒名）；
* 不填 → 也能绑定成功，风险由发布者现场核对承担。

为什么不强制必填：这两个字段本来就来自发布者登记的名单，让学生为了绑定
再去问一遍自己的手机号后四位，会把"扫码即用"的体验毁掉。而真正需要拦的
场景（有人拿别人的码来签）在**签到环节**还有位置围栏与设备绑定两层把关。

### 8.2 签到页（`checkin_page.dart`）

四条硬规则，每条都有对应的测试守着：

| 规则 | 理由 |
|---|---|
| **进页面不自动采集定位** | 方案 §7 只按需采集。一进页面就取定位，等于把权限弹窗强加给只是来浏览的用户 |
| **提交前只显示"正在由服务端判定"** | 验收 A15。若客户端先显示成功，服务端一旦判待确认/驳回，用户已经走开了 |
| **窗口未开/已关时说明原因与下一步** | 方案 §7「不得出现死路」。只把按钮灰掉，现场只会得到"按钮点不动"的困惑 |
| **隐私说明放在按钮上方** | 用户按下按钮前就应知道要采集什么 |

本地只做一层粗筛（经纬度有限且不是 `(0,0)`），与服务端 `hasFix` 同口径。
**本地不判定是否在围栏内**——只显示"约 XX 米（仅供参考）"，
帮用户决定要不要再走近一点。界面措辞刻意与判定区分开。

离线时直接入队（不等超时），并明确告知"超窗补传会转人工确认"——
否则用户会以为离线补传和正常签到一样能自动通过。

### 8.3 在岗确认页（`attendance_page.dart`）

**唯一的主操作是一个按钮「我在现场」，零输入**（验收 A17）。

这条不是体验优化，而是现场可用性的前提：志愿者可能正在搬书、
正在引导读者、手上戴着手套。要求任何输入，这个功能在真实场景里就不会被用。

两条不妥协：

1. **倒计时用服务端时间校正**（`ClockSkewMonitor`）。设备时间偏 5 分钟，
   用户就会"明明到点了却确认不了"。拿不到服务端时间时明确标注
   "时间可能不准"，**不假装准确**。
2. **没有定位证据不算完成**（验收 A19）。精度不达标时服务端返回
   `needsManualReview`，界面转成"已提交，待发布者确认"——
   这不是错误，但**必须让用户知道**，否则他会以为自己已经完成了。

超时后的文案必须包含"不自动扣减时长"（方案 §4.8），
`shared_ui` 的测试里有对应的断言。

### 8.4 记录页（`records_page.dart`）

**待上传队列放在最上面**，并逐条列出。

这一页的存在理由：弱网是常态（方案 §9），而离线证据如果没有明确的可见性，
用户会陷入两种糟糕状态——以为签上了其实还在队列里（事后争议），
或者不放心而反复点签到。

因此逐条显示：类型（签到证据 / 在岗确认）、入队时刻、已尝试次数、失败原因，
并给出「立即重试」。只给一个计数是不够的——用户最常问的正是
"我那条到底传上去了没有、是什么时候点的"。
