### A22 的实现位置与配套措施

**默认值**：`mock_server/src/constants.js` 的
`DEFAULTS.DEFAULT_ADMIN_INVITE_CODE = '1111'`，
由 `adminInviteCode()` 读取（`process.env.ADMIN_INVITE_CODE ?? 默认值`）。

**实测确认**（不只是读代码）：

```
未设环境变量：用 1111 登录 → 200 成功；用 1234 → 401 邀请码错误
设 ADMIN_INVITE_CODE=8888：用 8888 → 200 成功；用 1111 → 401 邀请码错误
```

最后一条很重要：**覆盖生效后旧默认码必须失效**。
如果 1111 仍能登录，说明"覆盖"只是多了一个码，那台机器上
实际上还留着一个公开口令。这条有测试钉住。

**⚠️ 固定默认码需要配套措施才可接受**，因此第三条测试专门断言：

| 配套 | 作用 |
|---|---|
| 登录必须携带 `deviceId`（设备指纹绑定） | 压小"1111 被谁拿到"的影响面 |
| 连续 5 次失败 → 10 分钟冷却（HTTP **423**） | 挡住暴力尝试 |

**这同时是一处文档冲突**（`docs/open-issues-app.md` O-1）：
README §3.3 底线①写"管理端不使用固定默认邀请码"，
而方案 §2/§14.1 与验收 A1/A2 都把固定默认码 1111 当作既定设计。
**当前按方案实现**，并已用上述两道措施补偿。
建议把 README 那句话改成"不使用固定默认码**而不加其他约束**"之类，
否则两处文档会长期互相矛盾。

## 测试怎么跑（含一个必须注意的坑）

```bash
# 服务端 Mock（156 项，含全部 A 系列）
cd mock_server && node test/smoke.js

# 共享内核 + 端到端联调（154 项；E2E 需要 Mock 在跑）
cd packages/shared_core && dart test

# 两端界面
cd packages/shared_ui && flutter test
cd apps/user_app      && flutter test
cd apps/admin_app     && flutter test
```

### ⚠️ 端到端测试必须**串行**

`packages/shared_core/dart_test.yaml` 里设了 `concurrency: 1`，**不要改**。

理由：E2E 打的是同一个 Mock 进程，而它用单个 JSON 文件持久化
（「读-改-写」）。多个测试文件并发写会互相覆盖，表现为若干断言偶发失败。
实测：串行 154 项全绿，并行 151 通过 / 3 失败。

这类 flaky 特别有害——它看起来像业务 bug，会让人去查根本不存在的逻辑错误。
全量跑一遍只要约 2 秒，不值得为并行省下的那点时间冒这个风险。

## 测试里不能依赖"全局计数"

`dart test` 默认并行，而 E2E 会不断创建活动与参与者。因此断言必须对
"别人也在写数据"保持免疫：

* ❌ 不要断言全局计数（`total`、`items.length`）
* ❌ 不要断言"游标之后为空"（别的文件可能刚好写了数据）
* ✅ 断言**属于本次创建的那个 id 的行为**
* ✅ 断言**不变量**（四态之和 = 有效名单人数、游标单调不减）

## 两处需要修订的用例文本（不是实现问题，是用例描述与既定决策不一致）

### A16

**原描述**：拒定位权限 → 提供降级路径（**动态签到码** / 管理端反向扫码 / 人工补录）

**实际情况**：本项目**不启用动态签到码**（决策 D-2）。降级路径只剩两条：

1. **发布者现场核实** —— 看板上点一下，`POST /activities/{id}/checkins/manual`，
   记录 `method = manual` 并写 `verifiedByOwner = true`；
2. **人工补录** —— 同一端点，用于设备故障、事后补录。

"不出现死路"这条要求仍然成立，且有两条测试守着。
**建议文本**：

> 拒绝定位权限时，志愿者不会被卡住：界面明确指向"请发布者现场核实"，
> 发布者可在管理端看板为其记录（`method=manual`、`verifiedByOwner=true`），
> 全程留痕可追溯。

**另外**：人工补录是**升级**已有的 `pending_review` 记录，
**不会插入第二条**（同一活动同一人只能有一条有效签到，方案 §6.1）。
这一点也有测试。

### A18 / A19 的适用前提

**原描述**没有说明"谁会被抽查"。

**实际情况**：抽查任务**只为已签到者生成**（决策 D-6）。因此：

> （仅对已签到的参与者生成在岗抽查任务）

不补这句的话，验收时可能会去检查"未签到的人为什么没有 `missed` 记录"，
而那是正确行为——给他记一串 `missed` 只会往考勤分母里灌水，
而方案 §13-A5 自己就承认抽查可能误判（"通知没到"被记成"人不在"），
分母越大越容易冤枉人。

## 需要真机确认的部分（A4 无法在模拟器完成）

以下**只能**在真实 Android 设备上确认，模拟器给不出可信结论：

| 项 | 为什么模拟器不行 |
|---|---|
| 定位精度与首次定位耗时 | 模拟器是注入坐标，没有真实的多径/冷启动行为 |
| 室内定位漂移（±30~100m） | 模拟器不存在这个现象，而它正是"待确认"最多的来源 |
| 弱网真实表现（2G / 地铁 / 地下车库） | 模拟器的网络是宿主机网络 |
| 厂商 ROM 的后台限制 | 国产 ROM 对后台网络/定位的限制差异极大 |
| 权限弹窗的实际文案与档位 | 各 ROM 的弹窗措辞与"仅本次允许"等档位不同 |
| 在岗抽查的通知可达性 | 现场"通知没到"是方案 §13-A5 自己承认的风险点 |

**建议的真机验证清单**（每条都应有明确结论，而不是"看起来还行"）：

1. 冷启动后首次签到：从点按钮到出结论的耗时是否可接受（目标 < 10 秒）；
2. 站在签到点旁边签：是否直接 `success`；
3. 走到 1.5 倍半径外签：是否 `rejected` 且提示距离；
4. 室内签到（如图书馆三层）：观察有多少落到"待确认"，以及精度数值范围；
5. 飞行模式下签到 → 恢复网络 → 确认自动补传且状态变为"待确认"；
6. 拒绝定位权限 → 确认界面给出"请发布者现场核实"而非死路；
7. 永久拒绝定位权限 → 确认"打开系统设置"按钮能真正跳到本应用设置页；
8. 在岗确认：从收到抽查到点下"我在现场"的耗时，以及倒计时是否与服务端一致；
9. 改手机时间 +5 分钟 → 确认倒计时仍以服务端时间为准；
10. 管理端登出后重进：是否要求重新输入邀请码。

> **第 4 项尤其重要**：自动通过门槛是 60 分，而单次采样只拿到围栏分（40）。
> 如果现场大量签到落到"待确认"，发布者的复核负担会失控。
> 这个比例必须在真机上实测，我无法在模拟器上给出可信数字。
