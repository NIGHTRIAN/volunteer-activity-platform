### 网络拓扑（与预期不同，值得记录）

```
        手机 Redmi Note 12T Pro
        ├── ap0   192.168.72.200/24   ← 手机自己是热点（SSID: 十文字斩）
        └── ccmni1 10.176.238.211     ← 蜂窝数据
                │
                └──(Wi-Fi)── PC 192.168.72.34  ← 跑 mock_server
```

**关键点**：手机是**热点主机**，PC 是它的客户端。因此：

* Android 热点默认开启**客户端隔离**，手机 **ping 不通** PC（100% 丢包）；
  但 **TCP 是通的**（`nc -z 192.168.72.34 8080` → REACHABLE）。
  → 排查连通性时**不要用 ping**，要用 TCP 探测，否则会误判成网络不通。
* 手机 Wi-Fi 客户端是**关闭**的（它在当 AP），所以
  `wifiBssid` 采不到、`getWifiIP()` 返回蜂窝 IP。见 O-17。

## 2. 安装：MIUI 的三道门禁

这是本次测试最大的时间黑洞，值得写清楚，因为**小米/红米机型都会遇到**。

### 现象与逐步排查

| 步骤 | 操作 | 结果 | 说明 |
|---|---|---|---|
| 1 | 插线后 `adb devices` | **空** | 系统只枚举出 `WPD`（文件传输），没有 ADB 接口 |
| 2 | 开「USB 调试」 | 设备出现，`adb install` 失败 | `INSTALL_FAILED_USER_RESTRICTED` |
| 3 | 开「USB 调试（安全设置）」 | `adb shell input` 可用，`install` 仍失败 | 该开关只放开**输入注入**，不含安装 |
| 4 | 开「**USB 安装**」 | ✅ 安装成功 | 这个开关才是关键，位置在「开发者选项」中部 |

### 三个开关的分工（容易混淆）

| MIUI 设置项 | 作用 | 不开的后果 |
|---|---|---|
| USB 调试 | adb 连接 | `adb devices` 看不到设备 |
| USB 调试（安全设置） | `input` / 权限修改 | `INJECT_EVENTS permission` 拒绝；`adb shell input` 全废 |
| **USB 安装** | 允许通过 USB 装 APK | `INSTALL_FAILED_USER_RESTRICTED: Install canceled by user` |

### 试过但**无效**的绕过手段（供后来者省时间）

以下全部返回同一错误，确认无捷径：

* `adb install` 各种参数：`--user 0` / `-g` / `--instant` / `--bypass-low-target-sdk-block` / `-d`
* `-i` 指定 installer 包名：`com.android.vending` / `com.miui.packageinstaller` / `com.google.android.packageinstaller`
* 分步会话安装：`pm install-create` → `install-write` → `install-commit`
* `adb push` 到 `/data/local/tmp` 后 `pm install`
* `adb root` → 生产版禁止（`adbd cannot run as root in production builds`）
* `settings put secure <key> 1` → 缺 `WRITE_SECURE_SETTINGS`，且 MIUI 该键根本不存在

### 备用路径（不依赖 adb 安装）

`adb push` 到 `/sdcard/Download/` 是**通的**（只是文件传输，不受门禁影响）。
所以实在开不了「USB 安装」时，可以把 APK 推到手机 `Download` 目录，
用文件管理器手动安装。本次未用到（第 4 步就通了），但已验证可行。

## 5. 为什么这些问题单元测试全绿？

这是本次测试最重要的收获，比缺陷本身更值得记住。

### 5.1 直接调 handler 的测试，掩盖了参数名契约

**O-13** 的测试是这样写的：

```js
api.respondAttendance(ctx({
  params: { id: fx.id, taskId: task.id },   // ← 手工把两个参数都塞进去
  ...
}));
```

真实路由只填 `taskId`，但测试自己补了 `id`。
**参数名一旦和路由脱节，"直接调 handler"的测试永远发现不了。**

→ 对策：新增**静态守卫**测试，扫描全部路由，把处理函数源码里读的
`ctx.params.X` 与路由模式声明的参数名逐一比对。一条测试覆盖所有接口。

### 5.2 按"理论报文"构造请求体，对不上真实客户端

**O-14** 的测试按扁平 `geoLat` 构造，而客户端发嵌套 `location.lat/lng`。
两套字段各自都能自洽，**只有真机把两端接起来才会暴露**。

→ 对策：回归测试刻意按客户端**真实**报文形状构造，并锚定注释
「这里刻意只传 taskId，因为真实路由也不会给活动 id」。

### 5.3 测试夹具会"帮忙"造出刚好可用的数据

**O-15** 的测试夹具把任务时间挪到 `now − 1min`，落在窗口内；
而真实场景里任务可能在未来。**夹具越好用，越容易掩盖边界**。

→ 对策：新增用例显式传 `activeTaskSeq: null`，
保留真实的未来时刻来验证"提前确认必须被拒"。

此外，修复 O-15 的第一版自己又踩了一个坑：
`Number.isFinite(parseTime(x))` —— `parseTime` 返回 **Date 对象**，`isFinite` 恒为 false，
**守卫被静默跳过**。是新写的测试当场抓到的。

### 5.4 状态字段依赖"有人手工设置"

活动状态 `published → ongoing` 的自动流转没有实现（已知 O-3），
但测试数据里的状态都是手工设好的，于是"到点了却点不了签到"这个
真机上必现的故障，在测试里**根本不存在**。

→ 对策：把"能不能签到"的判断从 `status` 改为**签到时间窗**，
并抽成纯函数 `checkinAvailability(activity, now)` 单独测试（7 条用例）。

#### 权限拒绝的实际表现（第一轮遗留项）

撤销定位权限后点「开始签到」，系统权限框弹出 → 点「拒绝」，App 显示：

> **需要定位权限**
> 签到需要一次定位作为在场证据（不采集持续轨迹）。若你不方便开启定位，可以请发布者现场核实。
> 点击「开始签到」会再次弹出系统授权框。

并且**服务端没有收到任何请求**（0 条签到记录）—— 不浪费一次注定失败的调用，
同时给了明确的替代路径（请发布者现场核实），符合方案 §7「不出现死路」。

#### 离线链路的完整验证方法

难点：关掉网络后 **GPS 也会超时**（A-GPS 需要网络辅助），
进不到「离线入队」分支。

解法：**停掉 mock_server，但保留手机网络**。
这样定位能正常采集（±30m），而 HTTP 请求失败 → 客户端判定为超时 → 入队。

验证步骤与结果：

| 步骤 | 结果 |
|---|---|
| 1. 停 mock_server（保留网络） | — |
| 2. 点「开始签到」 | 界面：**已保存到本机** +「联网后自动上传。上传时会由服务端判定，可能转人工确认。」+ `网络超时 code=-2` |
| 3. `adb shell am force-stop` 杀掉 App | 进程退出（模拟被系统回收） |
| 4. 重启 mock_server | — |
| 5. 重新打开 App | **自动补传**：服务端出现记录，`offlineBackfill=true`，状态 `pending_review` |

> 离线补传的记录按设计转人工确认（防事后补造证据），这是预期行为。

#### 管理端人工复核（第一轮遗留项）

用管理端打开自己名下的活动 →「现场看板」→「待确认 1 人」→ 点名单行进入复核页。

复核页展示的信息（这是"让发布者做决定"的关键）：

* **客观证据**：提交时间、方式（定位签到）、距签到点 0 米、定位精度 ±25 米
* **证据评分 40 分** + 说明「自动通过需 ≥60 分；30–59 分转人工（就是当前这条）。**评分只是辅助，最终由你判断。**」
* **评分明细**：`+40 围栏内且距中心 0m（≤50m）` / `0 多次采样差异较大`
* 备注输入框（200 字符）
* 「驳回」/「通过」两个按钮
* 页脚：复核结论会立即写入记录，并显示在该志愿者的「我的记录」里

点「通过」之后：

```
界面:      已通过
服务端:    状态=success
           复核人=owner-mvcchx26m0glavl3
           复核于=2026-10-17T20:06:09+08:00
名单状态:  checked_in
```

**评分明细能解释"为什么是这个分"这一点很重要** ——
否则发布者面对一个"40 分"只会觉得系统在为难人。

| O-21 | **跨发布者越权**：管理员能看到所有人的活动 | 🔴 | 新增 `optional` 鉴权，`/activities` 与 `/changes` 改用它 |
| O-22 | `/dev/*` 无环境守卫、`/activities/organizers` 路由缺失 | 🟡 | 部分修复，待确认 |

详细根因与回归测试见 `docs/open-issues-app.md` 的 O-18 ~ O-23。

### 10.3 这一轮的共同教训

这一轮的 4 个主要缺陷有一个共同的形状：

> **界面在承诺一件代码没做的事。**

* 「已保存到本机」→ 队列只在内存里
* 「联网后自动上传」→ 没有自动触发点
* 「我发布的活动」→ 列表没按发布者过滤
* 「绑定成功」→ 响应丢了就永远绑不上

比直接报错更危险：**错误会让人补救，虚假的成功提示不会**。
用户会带着"我已经交上去了"的错觉离开现场，直到事后被判定缺席。

对应的测试方法也值得记住：

* 队列持久化这类"进程生命周期"问题，**单元测试天然测不到** ——
  必须真机 `force-stop` 再重启；
* 归属隔离这类问题，**用两个不同身份各查一次**立刻暴露；
* `optional` 鉴权这类"配置缺失导致逻辑静默降级"的问题，
  最经济的防线是**静态守卫测试**（断言路由声明的 auth 模式）。

## 11. 第三轮：场地网络白名单（O-17）与一个静默的 IP 误取 bug

### 11.1 为什么 O-17 不是"缺个字段"那么简单

评分表（方案 §6.1）：

```
围栏内（精度 ≤50m）   +40
多次采样一致          +10
                     ─────
                     50   ← 自动通过门槛是 60
```

差的 10–30 分**只能**来自网络辅证（Wi-Fi +20 / 校园网 +10），
而服务端只在**活动配置了白名单**时才计分（"无法证明就不参与判定"，
否则谁都能填个 BSSID 骗分）。

结论：**发布者不配白名单，志愿者每次签到都会转人工确认。**
现场发布者要逐条点复核 —— 这直接决定产品能不能用。

同一条因果链也意味着：**没有白名单录入，连"自动通过"都没法演示。**

修复前：新建活动页没有任何网络字段。
修复后：新增「场地网络（可选，但强烈建议配）」区块，
一键「用当前网络作为场地网络」，自动读 BSSID + 本机 IP 网段。

已用测试钉住三种情形：

| 活动配置 | 提交证据 | 总分 | 结果 |
|---|---|---|---|
| 不配白名单 | 围栏内 + 采样一致 | 50 | `pending_review` |
| 配 `10.3.` | 上述 + `sourceIp=10.3.215.117` | 60 | **`success` 自动通过** |
| 配 `202.119.` | 上述 + `sourceIp=192.168.72.100` | 50 | `pending_review`（不能白送分） |

### 11.2 真机暴露的 bug：`getWifiIP()` 拿到的是蜂窝地址

**现象**：在管理端点「用当前网络作为场地网络」，结果显示

```
场地 Wi-Fi：06:74:9c:e6:12:5f（+20 分）
校园网网段：10.176.（+10 分）      ← 可疑
```

而同一台手机的接口列表是：

```
ccmni1  10.176.238.211/8     ← 蜂窝
wlan0   10.3.229.13/16       ← Wi-Fi
```

`NetworkInfo.getWifiIP()` 返回的是 **`10.176.238.211`（蜂窝）**，不是 Wi-Fi 地址。

**后果（全是静默的）**：

1. 发布者录到的网段与场地 Wi-Fi 无关；
2. 志愿者上报的 `sourceIp` 同样是蜂窝地址，"恰好"和发布者一致，
   看起来能用 —— 实际上任何同运营商网段的人都可能命中；
3. 一旦有人只开 Wi-Fi 不开移动数据，他上报 `10.3.` 而白名单是 `10.176.`，
   **永远命中不了**，于是这个人每次签到都要人工确认。

**为什么单测没抓到**：测试机没有双链路（Wi-Fi + 蜂窝同时活动），
列表顺序由系统决定，蜂窝常常排在前面。

**修复**：不再问插件，按**接口名**取地址（纯 Dart，可测）。

```
优先级：wlan > swlan > ap > eth
排除：ccmni / rmnet / pdp（蜂窝）、p2p（Wi-Fi Direct）、127.* / 169.254.*
```

抽成纯函数 `ConnectivityService.pickWifiAddress(List<(String,String)>)`
后用真机实测的接口名写了 5 项测试。

修复后真机复测：

```
场地 Wi-Fi：06:74:9c:e6:12:5f（+20 分）
校园网网段：10.3.（+10 分）        ← 与 wlan0 一致 ✓
```

> 教训：**凡是"系统告诉我一个值"的地方，都要用另一个独立来源交叉验证一次。**
> 这个 bug 不会让任何测试失败，只会让一条业务规则静默失效。

## 12. 第四轮：离线模式"永远转人工"—— 字段名对不上的静默失分

### 12.1 现象

离线演示模式跑通后，签到结果稳定停在 **40 分（待人工确认）**。
按评分表，围栏内且精度好应得 40，多次采样一致再 +10，校园网命中再 +10，
配了白名单后**应该 60 分自动通过**。实际只拿到 40 —— 两项加分全部没算。

### 12.2 根因：演示引擎按"直觉"读字段，与生产序列化器不一致

客户端真实上送（`CheckinDraft.toJson()`）：

```json
{
  "location": { "lat": …, "lng": …, "accuracy": …, "samples": [ … ] },
  "network":  { "wifiBssids": ["aa:bb:…"], "sourceIp": "10.3.229.13" },
  "device":   { "mockLocationDetected": false }
}
```

而演示引擎里写的是：

| 引擎读的 | 实际字段 | 后果 |
|---|---|---|
| `body.samples` | `location.samples` | 采样数恒为 0 → 丢 10 分 |
| `network.wifiBssid`（单数） | `network.wifiBssids`（数组） | Wi-Fi 永不命中 → 丢 20 分 |
| `network.localIp` | `network.sourceIp` | 校园网永不命中 → 丢 10 分 |

三项全错，但**没有任何报错** —— 只是分数少了几十分。
于是所有签到都变成"待人工确认"，看起来像"自动通过功能没做好"。

### 12.3 为什么测试没抓到（这才是重点）

测试里我是**手写 JSON 载荷**的，而手写的形状恰好和引擎的读法一致
（都是"扁平直觉版"）。生产代码与测试代码用了**两套不同的字段名**，
于是双方一起错、互相印证 —— 测试全绿，功能全废。

**修复方式不只是改字段名，而是改测试的数据来源：**

```dart
// ❌ 以前：手写，可能与生产漂移
body: {'location': {...}, 'samples': [...]}

// ✅ 现在：直接喂生产序列化器的输出
body: CheckinDraft(...).toJson()
```

用同一个序列化器之后，这类漂移**在结构上不可能再发生**。

### 12.4 修复后的真机复测

```
距签到点   约 0 米
证据评分   60（服务端计算，仅供参考）
状态       已签到        ← 自动通过
```

拆解：围栏 40 + 采样一致 10 + 校园网命中 10 = 60，正好过门槛。

### 12.5 教训

1. **测试的输入必须来自生产的序列化器**，不能手写。
   手写载荷测的是"我以为的协议"，不是"实际发出的协议"。
2. **静默失分比报错更危险**：三项加分全丢，界面仍然一切正常，
   只是结果永远是"待人工确认"。没有任何一处会报错。
3. 演示引擎虽然只是演示用，但它复用的是**评分规则**，
   所以它读错字段 → 演示结论就是错的 → 验收者看到的就是错的产品印象。

## 13. 第五轮：人工复核返回「接口不存在」—— 路径形态对不上

### 13.1 现象

管理端点「通过」复核签到，界面提示 **「接口不存在」**。
这是管理端最核心的动作之一，等于这条链路完全不可用。

### 13.2 根因：路径段 vs 动作后缀

契约里两种写法都有，容易混：

| 客户端 | 客户端拼出来 | 服务端注册的 | 结果 |
|---|---|---|---|
| `CheckinPaths.review(id)` | `/checkins/{id}/review` | `/checkins/:checkinId:review` | ❌ 404 |
| `AttendancePaths.confirm(id)` | `/attendances/{id}:confirm` | `/attendances/:taskId:confirm` | ✅ |

**复核是「路径段」形式，在岗确认才是「动作后缀」形式。**
服务端把复核也写成了 `:review`，于是它永远匹配不上 `/checkins/5/review`。

### 13.3 为什么测试没抓到（这才是重点）

`checkin.test.mjs` 里手写的路径**同样是错的** `:review`：

```js
// 错：测试和实现一起错，互相印证
await call('POST', `/api/checkins/${id}:review`, ...)
```

这和第四轮的"字段名对不上"是**完全同一类错误**：
**测试用了自己以为的协议，而不是客户端真正发出的协议。**

修复不只是改一行路由，而是加了两侧锁：

| 文件 | 锁什么 |
|---|---|
| `server/test/routes.test.mjs` | 用客户端真实路径字符串逐个问路由器"认不认识" |
| `packages/shared_core/test/api_paths_test.dart` | 锁住每个构造器拼出的确切形态 |
| `checkin.test.mjs` | 改用真实路径 `/review` |

任一侧改动，都会有一个测试变红。

### 13.4 顺带发现的 11 个「契约有、服务端没有」的接口

路由测试一跑就列出来了（客户端 `api_paths.dart` 已声明，但服务端未实现，
当前两个 App 与网页都还没用到）：

```
GET  /auth/admin/me              GET  /activities/{id}/changes
GET  /auth/admin/audits          GET  /activities/{id}/invite-codes
GET  /auth/admin/export-audits   POST /activities/{id}/checkins/manual
GET  /auth/me                    POST /attendances/{id}:remind
PATCH /activities/{id}           POST /activities/{id}/attendance/manual
GET  /changes
```

这些被显式列进 `routes.test.mjs` 的 `PENDING` 清单：
不假装已实现，也不让它们悄悄消失。谁实现了就把条目移到 `REQUIRED`，
那时才会被真正校验。

### 13.5 修复后真机复测

```
看板：待确认 1 人（待复核人 2025002，评分 50）
→ 点他进复核页 → 证据明细正常
→ 点「通过」
→ 显示「已通过」
→ 返回看板：已签到 1 人 / 待确认 0 人 / 名单显示「已签到」
```

同时用 HTTP 直接验证两种形态：

```
POST /api/checkins/1/review   → HTTP 200, code 0, status=success
POST /api/checkins/1:review   → HTTP 404「接口不存在」（旧错形态）
```

### 13.6 教训

1. **测试里的 URL 必须来自客户端的构造函数**，不能手写。
   手写 = 测试自己以为的协议，与真实发出的协议可能不一致。
2. 同一个 API 里同时存在"路径段"与"动作后缀"两种风格时，
   **最容易照着旁边那行抄错**。现在有专门的测试把两种形态各自钉住。
3. 路由层缺陷的表现是 404「接口不存在」，看起来像"功能没做"，
   而不是"写错了"—— 所以要用"路由表 vs 客户端路径清单"这种
   结构性校验，而不是靠零散用例。

### 14.5 一个环境坑（记下来免得再踩）

「看板归属隔离」这条一开始怎么都不过。原因不是服务端：

> e2e 的 `loginAs()` **固定用邀请码 `1111`**，
> 而**真实服务端的 ownerId 来自邀请码**（不是设备指纹 —— 早先按设备指纹算，
> 导致"我发布的活动 0 条"，已修）。
>
> 所以 `loginAs('other')` 和 `loginAs('owner')` 其实是**同一个发布者**，
> 隔离自然测不出来。

修法：用例支持传第二个邀请码（`E2E_ADMIN_CODE_B`，默认 `2222`），
服务端用 `ADMIN_OWNERS='1111:owner-a,2222:owner-b'` 启动；
**单发布者部署时该用例自动跳过**，而不是误报失败。

### 14.6 教训

1. **端到端用例必须对真服务器跑一遍。** 只对 mock 跑，等于只测了
   "客户端与 mock 是否一致"，没测"服务端是否实现了同一份契约"。
2. **默认值能掩盖 bug。** `ImportRowResult.accepted` 默认 false，
   字段名写错时不报错、只是所有行都显示失败 —— 这类要靠内容断言。
3. **别在测试里手写请求。** 两条 e2e 用例用的都是
   `CheckinPaths.review()` / `ActivityPaths.transition()` 这类构造器，
   这次正是它们抓出了路径与字段的偏差。
