## 1. 项目定位与目标

### 1.1 定位

本平台是**活动发布与参与的协作平台**，为活动发布者与志愿者提供更直接、方便的参与与获知渠道。**不作为志愿时长统计与认定的权威依据。**

定位决定治理强度，三类事务分别处理：

| 事项 | 强度 | 说明 |
|---|---|---|
| 数据**准确性**（名单、签到、考勤记录） | **必须保证** | 否则组织者无法用它协调现场，功能本身失去意义 |
| 数据**保密性** | **合理即可** | 不做存储加密与字段级报表审计；保留三条零成本底线（见 §9.1） |
| 考勤判定结果 | **参考信息** | 供现场管理参考，**不自动产生任何时长扣减或权益影响** |

### 1.2 目标

- 「软件一」（**管理端 App**）发布的活动可被稳定接收、校验、落库；
- 平台提供活动列表与详情（主要信息展示、详细信息折叠，信息对照清楚）；
- 平台以图表呈现汇总统计；
- 「软件二」（**用户端 App**）可浏览活动、上报签到，并查看本人记录；
- 浏览者可导出活动信息并在本机收藏；
- **服务端为状态权威**：活动状态由服务端持有，三端看到同一状态。

### 1.3 范围内

数据接收、存储与校验、**状态机与审计**、**规则快照**、邀请码与活动授权、签到与防脱岗考勤、名单维护、导出、活动列表页、详情（折叠）、统计图表、面向 App 的全部接口、部署与运维、基础安全。

### 1.4 范围外

- 志愿时长的认定与结算（平台只提供参考信息）；
- 志愿者实名认证（身份由发布者核验）；
- Web 浏览端的账号体系（公开只读）；
- 移动端 App 的界面实现（由移动端方案承接）；
- 平台内自助报名审批流（名单由发布者维护）。

### 4.5 在岗考勤 `attendance_task`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `activityId` / `userId` | — | 主键与归属 |
| `seq` | int | 第几次抽查（`(activityId, userId, seq)` 唯一） |
| `scheduledAt` / `deadlineAt` | datetime | 应确认时间 / 响应截止（默认 +5 分钟） |
| `status` | enum | `pending` / `done` / `missed` / `excused` |
| `checkinId` | int | 完成时关联 |
| `notifiedAt` | datetime | 提醒下发时间（区分"人不在"与"通知没到"） |

**典型结果**：2 小时活动抽查 **3 次**（T+15 / T+45 / T+75）。

### 4.6 动态签到码 `checkin_code`（降级手段）

| 实体 | 量级 |

## 5. 状态机与规则

### 5.1 状态与转移

```
draft ──发布──▶ published ──开始──▶ ongoing ──宣布结束/自动结束──▶ finished
  │                 │                  │
  └────取消─────────┴──────────────────┴──▶ cancelled（终态，不可逆）
```

| 转移 | 触发者 | 前置 | 副作用 |
|---|---|---|---|
| `draft` → `published` | 管理端 | 必填齐全 | 对外可见；**冻结规则快照**；写变更日志 |
| `published` → `ongoing` | 管理端 或 定时 | 到达 `startTime` 或手动开始 | 开放签到窗口 |
| `ongoing` → `finished` | 管理端（**宣布结束**，二次确认） | — | 关闭签到与抽查；生成考勤汇总；通知志愿者 |
| `ongoing` → `finished`（兜底） | 定时任务 | 到达 `endTime` 且未手动结束 | 同上；**手动优先** |
| 任意非终态 → `cancelled` | 管理端（**取消**，二次确认） | 原因 ≥5 字 | 见 §5.3 |

规则：非法转移 `40901`；越权 `40301`；每次转移记录 **actor + 时间 + 原因**；变更写入变更日志供增量接口下发。

### 5.2 规则快照（发布即冻结）

发布时把判定相关规则写入**不可变快照**：`startTime`、`endTime`、`durationHours`、签到窗口与半径、抽查参数、时长折算系数。

- 判定一律按快照执行，**永不追溯改写**已产出的判定；
- 发布后**关键字段默认禁止修改**；确需修改 → 填写原因 → 记录前后值 → 通知已绑定志愿者 → 生成新版本快照，**仅对未来生效**；
- 非关键字段（简介、详情、联系方式、备注）可自由修改；
- 目的：判定依据不被事后改写，**同时是管理者的争议证据**。

### 5.3 取消规则（不可逆）

1. **未开始即取消**：签到与抽查记录保留并标注"活动取消"，**不计入任何判定**；
2. **已开始后取消**：已发生的抽查按实际结果保留；**未发生的任务置 `excused`**（不计入分母）；
3. 已绑定志愿者收到取消通知；
4. 不可恢复（需继续请新建活动），避免状态反复与争议；
5. 取消原因写入审计。

### 5.4 数据权威与变更规则

- 活动主体字段以**管理端 App**为准；服务端持有 `status` 与 `ruleSnapshot`；
- 同一 `externalId` 重复上报视为更新（幂等）；**不允许通过重传覆盖服务端已流转的状态**；
- 删除采用软删除，保留审计；
- `participant` / `checkin` / `attendance_task` 由服务端权威存储，全部留痕。

### 6.3 鉴权与身份

**管理端**（详见《接口契约》§4.4）

```
POST /api/v1/auth/admin/login    { "inviteCode": "1111", "deviceId": "..." }
     → 默认邀请码 1111（服务端可配置修改）；连续 5 次失败锁定 10 分钟
```

- **管理员邀请码默认 `1111`**，可在服务端配置修改（系统所有者可改为随机码或一人一码）；
- **不强制更换**：默认码是全体管理者共用的入口，强制更换会导致其他管理者无法登录；如需独立码，由系统所有者按人配置；
- **已接受的残余风险**：任何取得管理端 App 的人都能以管理者身份进入。因此**必须**依赖以下三项缓解：
  1. **`ownerId` 归属隔离**——越权者只能操作自己创建的活动，无法触碰他人活动；
  2. **设备指纹绑定**——首次登录后与该设备绑定；
  3. **登录审计**——记录时间、设备、IP，便于事后发现异常；
- 管理者**只能操作自己创建的活动**（服务端逐接口校验 `ownerId`）；
- 令牌有效期 = 名下活动存续期；全部活动进入终态后 **24 小时**失效。

**用户端最小身份**（详见《接口契约》§4.3）

```
POST /api/v1/auth/bind           { "userNo": "2021xxxx", "inviteCode": "******", "deviceId": "..." }
     → 校验：邀请码有效且未用 & userNo ∈ 该活动名单 → 签发 deviceToken + activity_grant
```

- 生命周期：`grant.expiresAt = 活动终态 + 7 天`（申诉与补传宽限）→ 到期撤销授权 → 无剩余授权时销毁令牌与身份绑定关系；
- **销毁的是凭证与身份关联，不是业务记录**（签到、考勤、审计按留存期保留）；
- 多活动并发：令牌按人、授权按活动；全部授权过期后令牌才失效。

#### 6.4.1 活动上报

响应含 `accepted / created / updated / rejected[]`（**部分失败仍返回 200**，非法条附原因）。

#### 6.4.2 状态流转

```
POST /api/v1/activities/{id}:transition
{ "from":"ongoing", "to":"finished", "reason":"现场活动已结束" }
```

#### 6.4.3 名单维护（发布者）

```
POST   /api/v1/activities/{id}/participants                # 单个或批量
POST   /api/v1/activities/{id}/participants:import         # CSV/Excel，逐行返回结果

```

导入校验：学号格式、活动内重复、（可选）姓名/手机号后四位二次校验；**移出名单不删除历史签到与考勤记录**，仅标注"已移出（时间）"。

#### 6.4.4 邀请码发放（发布者）

```
POST /api/v1/activities/{id}/invite-codes   { "userNo":"2021xxxx" }   → 返回一次性邀请码（仅显示一次）
```

#### 6.4.5 签到（用户端）

```
POST /api/v1/activities/{id}/checkins
{ "method":"geo",
  "location":{"lat":34.2172,"lng":117.1438,"accuracy":18.5,"provider":"gps","samples":3,"sampledAt":"…"},
  "network":{"wifiBssids":["a4:2b:8c:11:22:33"],"sourceIp":"202.119.x.x"},
  "device":{"deviceId":"…","mockLocationDetected":false},
  "clientTime":"2025-03-01T09:02:11+08:00" }
```

**判定（服务端，顺序）**：① 活动状态与签到窗口；② 是否重复（按活动唯一）；③ **客观证据评分**（下表）；④ 降级方式（`method=qrcode`）校验动态码。

| 证据 | 分值 | | 减分项 | 分值 |
|---|---|---|---|---|
| 围栏内且 `accuracy ≤50m` | +40 | | **检测到模拟定位** | −60 且强制转人工 |
| 围栏内且 `accuracy` 50～100m | +25 | | 同设备多账号 | −30 |
| 签到前 60 秒内已有围栏内定位 | +15 | | 轨迹/速度异常 | −40 |
| Wi-Fi BSSID 命中（Android） | +20 | | `accuracy > 100m` | 该证据不计分 |
| 校园网出口 IP 命中 | +10 | | | |
| 停留验证通过（10 分钟内再次在场） | +15 | | | |
| 多次采样一致（离散度 ≤30m） | +10 | | | |

**判定**：**≥60 → `success`**；**30～59 或命中模拟定位 → `pending_review`**；**<30 → `rejected`**（附原因）。
坐标系强制 **WGS-84**；高德/腾讯/百度 SDK 须先转换（GCJ-02/BD-09 与 WGS-84 相差 50～500m）。评分阈值可配。

#### 6.4.6 在岗确认（用户端）

```
POST /api/v1/attendances/{taskId}:confirm   { "method":"geo", "location":{...}, "device":{...} }
```

- 前置：存在 `status='pending'` 且 `now ≤ deadlineAt` 的任务，否则 `NO_PENDING_TASK`；
- **不启用推送**：志愿者在 App 的"待确认任务"入口看到抽查后点击即完成（App 自动定位上报），**零输入、零扫码**；管理端可现场口头催办；
- 成功置 `done`；超时由服务端定时任务置 `missed`。

#### 6.4.7 考勤汇总（参考信息）

```
GET /api/v1/activities/{id}/attendance
```

判定：`full`（无 missed）/ `partial`（完成率 ≥0.7）/ `insufficient` / `absent`；输出**明细与参考值**，**不产生任何自动扣减**。

#### 6.4.8 导出（统一入口）

```
GET /api/v1/activities/{id}/export?format=csv
GET /api/v1/export/activities?dateFrom=&dateTo=&status=finished&format=csv
```
服务端生成（UTF-8 BOM），三端共用；含个人信息时附"仅限内部使用"提示；用户端仅可导出已结束活动。

#### 6.4.9 增量同步

```
GET /api/v1/changes?since=<cursor>&limit=200    → { nextCursor, hasMore, items:[{op,id,...}] }
```
游标 7 天幂等窗口；降级方案为时间窗拉取。

### 6.5 非功能指标

| 指标 | 目标 |
|---|---|
| 端到端同步延迟 | ≤ 60s |
| 上报峰值 | ≤10 次/分钟（按 3 倍余量建设） |
| 列表接口 P95 | < 800ms |
| **签到峰值** | 活动开始前后 5 分钟内 **300 并发**，P95 < 800ms，幂等正确 |

## 8. 部署形态与服务器对接规格

> **本阶段不搭建生产服务器。** 开发与联调在本地/容器环境完成，生产服务器**后续租用**。本节把"服务器必须提供什么"固化为**对接规格**——未来租用时照此采购与交付，**代码与配置无需改动**。

### 8.1 本阶段的运行形态

| 环境 | 载体 | 用途 |
|---|---|---|
| 本地开发 | 开发者机器 + Docker Compose（MySQL + 同步服务） | 日常开发 |
| 本地/容器联调 | 同一 Compose 栈（可接 Mock 或真实服务） | 与两端 App 联调 |
| 内网联调 | 开发机局域网 IP 或内网穿透（frp / cpolar / ngrok） | **真机测试**（App 需能访问） |

**可移植性要求（本阶段就必须满足，否则未来迁移会返工）**

1. **服务端地址、端口、凭据全部走配置**（环境变量 / `.env`）；代码中**不得硬编码**域名、IP、端口；
2. 提供 **`docker-compose.yml`**：一条命令拉起 MySQL + 同步服务，**在任意机器可复现**；
3. 提供 **`.env.example`** 与**部署文档**，未来服务器落地时按文档执行即可；
4. 数据库初始化脚本（DDL + 基础数据）随仓库提供；
5. 启动方式与环境无关：本地、容器、云服务器**同一套命令**。

### 8.4 服务器容量参考（未来采购时对照）

| 场景 | CPU / 内存 | 磁盘 | 带宽 |
|---|---|---|---|
| 生产 · 不接入 TDUCK | 2 核 / 4 GB | 40 GB SSD | ≥5 Mbps（配 CDN） |
| 生产 · 接入 TDUCK（同机） | 4 核 / 8 GB | 60 GB+ SSD | 5–10 Mbps |

**两条红线**：**2 核 2 GB 不足**（Nginx + JVM + MySQL 合计约 2 GB，且 MySQL 8 的 `performance_schema` 会加剧内存压力 → 易 OOM）；**1 Mbps 不足**（首屏静态资源约 400 KB，数人同时打开即打满）。
**扩容触发**：内存持续 >80% 或 OOM / 列表 P95 >800ms / 磁盘 >70% / 签到高峰 5xx。
**扩容顺序**：先加内存 → 再拆云数据库 → 最后加应用节点。

**安全组最小开放**：公网仅 **80 / 443**；8080 / 8998 / 8999 / 3306 仅内网或本机；SSH 限来源 IP。

### 8.6 TDUCK 社区版（可选，随服务器落地）

**获取**：① 官方部署包（公众号回复「部署文件」）；② 源码编译（`tduck-platform` + `tduck-front`，两者均需）。
**硬约束**：**JDK 1.8 强制**；MySQL 5.7+（`utf8mb4` + JSON）；**社区版用 Ehcache，无需 Redis**；源码编译需 Node ≥14、Maven ≥3.6。

**部署后立即修改默认账号**（v4/v5/v6 为 `admin@tduckcloud.com / 123456`）——默认值不得保留。
**安全事实**：社区版后端**默认未注册签名校验过滤器**，请求直接通行；示例 `secret` 写死在前端。所有设防须在 Nginx 与自建服务层完成。

## 9. 安全与合规

### 9.1 三条零成本底线

1. **管理端邀请码默认 `1111`**（服务端可配置；**已接受该风险**）——以 `ownerId` 归属隔离 + 设备绑定 + 登录审计控制影响面；
2. **日志不打印完整手机号**等个人信息；
3. **导出文件带"仅限内部使用"提示**（含个人信息时二次确认）。

### 9.2 权限

管理者**只能操作自己创建的活动**（`ownerId` 校验）；名单、考勤、复核、导出逐接口校验；越权 `40301`；所有权转移留审计。

### 9.3 其他

- 全站 HTTPS（TLS 1.2+）；关键接口 IP 白名单（上下游 IP 固定时）；
- 凭据不入文档与仓库；交付用独立凭据交接单；
- 富文本双重白名单过滤（服务端 + 前端）；
- **数据留存统一为 7 天**：活动进入终态（`finished` / `cancelled`）后 **7 天**，**一并删除**业务数据（活动、参与者、签到、考勤任务）、位置证据、审计日志与全部凭证；**仅保留销毁日志**（作为"已删除"的证明）；
- 到期前 **48 小时**提醒发布者导出；**发布者必须在窗口内完成导出与对账，逾期数据不可恢复**；
- 上述留存期写入隐私政策。

| T3 | 批次中 1 条非法 | 合法入库，非法条驳回，HTTP 200 |
| T4 | 发布活动 | 生成**规则快照**；修改关键字段被拒或转入"需填原因"流程 |
| T5 | 修改已发布活动的起止时间 | 记录前后值、通知志愿者、**新快照仅对未来生效**，历史判定不变 |
| T6 | 管理端 A 操作管理端 B 的活动 | 返回 `40301`，数据不变 |
| T7 | 管理端用默认邀请码 `1111` 首次登录 | 登录成功；绑定设备指纹并签发令牌 |
| T8 | 用默认邀请码 `1111` 登录管理端 | **登录成功**（默认码为既定设计）；同时验证**登录审计已记录**（时间/设备/IP） |
| T9 | 连续 5 次错误邀请码 | 账号锁定 10 分钟 |
| T10 | 志愿者用邀请码绑定 | 校验名单通过后签发设备令牌与活动授权 |
| T11 | 非名单用户绑定 | 拒绝并给出明确原因 |
| T12 | 围栏内签到（`accuracy ≤50m`） | `success`，评分 ≥60 |
| T13 | 距场地 1.5 倍半径外签到 | `rejected`，原因"超出签到范围" |
| T14 | 开启模拟定位后签到 | 命中 → **强制 `pending_review`**，不自动通过 |
| T15 | 高德 SDK 坐标未转换即上报 | 被识别为坐标偏移异常（坐标系回归用例） |
| T16 | 同一活动重复签到 | 幂等，仅一条有效记录 |
| T17 | **跨天活动**（22:00–次日 02:00）签到 | 正常受理，**不被误判为重复** |
| T18 | 在岗抽查：点开通知 | 自动定位上报 → `task=done`，**无需任何输入** |
| T19 | 在岗抽查：超时未响应 | `missed`，且存在通知记录 |
| T20 | 2 小时活动默认配置 | 生成 3 次抽查（T+15 / T+45 / T+75） |
| T21 | 取消已开始的活动 | 未发生任务置 `excused`；已发生的保留；志愿者收到通知 |
| T22 | 活动结束后 7 天内补传签到 | 受理并记 `pending_review` |
| T23 | 授权过期后访问该活动 | 拒绝；业务记录仍可按留存期查询 |
| T24 | 导出 CSV | 字段一致、中文不乱码（UTF-8 BOM）、含"仅限内部使用"提示 |
| T25 | 详情 `description` 含 `<script>` | 被过滤，不执行 |
| T26 | 服务端日志抽查 | **不含完整手机号** |

### 11.3 非功能验收

- 200 并发只读，列表 P95 < 800ms，错误率 < 0.1%；
- **300 并发签到**（活动开始前后 5 分钟）P95 < 800ms，无重复记录；
- 拔掉 MySQL 后服务不崩溃，恢复自愈；
- Web 端 375px 宽可正常浏览与展开详情；
- App 端弱网/离线无数据丢失、无重复、状态提示准确。
