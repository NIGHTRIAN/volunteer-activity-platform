## O-1　管理端默认邀请码：方案内部直接冲突 🔴

| 位置 | 原文 |
|---|---|
| 移动端方案 §2 关键决策 | 「管理端身份：**管理员邀请码默认 `1111`**（服务端可配置）；**不强制更换**；连续 5 次失败锁定 10 分钟」 |
| 移动端方案 §14.1-1 已定事项 | 「管理端邀请码：**默认 `1111`**（服务端可配置）；**不强制更换**；依赖 `ownerId` 隔离 + 设备绑定 + 登录审计」 |
| 移动端方案 §12 验收 A1 | 「用默认邀请码 `1111` 首次登录管理端 → **登录成功**」 |
| 移动端方案 §12 验收 A2 | 「用默认邀请码 `1111` 登录管理端 → **成功**（默认码为既定设计）」 |
| **README §3.3 三条零成本底线①** | 「管理端**不使用固定默认邀请码**」 |

**矛盾点**：§2/§14.1/A1/A2 都把固定默认码 `1111` 当作**既定设计并写成验收标准**，
而 README §3.3 把它列为**必须避免的安全底线**。

**我的取舍**：**按 §2/§14.1/A1/A2 实现**。

理由：
1. 移动端方案是**执行依据**，README 是**交付包总览**；前者更具体、更新更晚（含验收用例）。
2. 验收 A1/A2 是**可判定的断言**，而底线①是原则性表述。
3. §13-A1 已明确记录"已接受该风险"，并给出了收紧路径——说明这是**有意识的取舍**，
   不是疏漏。README §3.3 的表述与这个取舍不同步。

**已实现的风险缓解（§2 三项全部落地）**：
* ✅ `ownerId` 归属隔离 —— 越权返回 `40301`（验收 A4 通过）
* ✅ 设备指纹绑定 —— 换设备新建 owner，且校验 `X-Device-Id`
* ✅ 登录审计 —— 记录时间/设备/IP，且**不含完整手机号或学号**

**服务端可配置是真的可配置**：环境变量 `ADMIN_INVITE_CODE` 可覆盖，
并有测试覆盖（`§13-A1 收紧路径：环境变量可覆盖默认邀请码`）。

**★ 需要你决定**：README §3.3 底线①要不要改成与 §2 一致的表述？
若坚持底线①，则验收 A1/A2 必须改，且管理端需要一套"按人发码"的机制（§13-A1 的收紧路径）。

## O-2　末次抽查留白：15 分钟还是 30 分钟 🔴

| 位置 | 原文 |
|---|---|
| §6.2 | 「首次 `startTime + 15min`，间隔默认 30 分钟，**末次不晚于 `endTime − 15min`**」 |
| §6.2（同一段） | 「→ **2 小时活动 3 次**（T+15 / T+45 / T+75）」 |

**矛盾点**：留白 15 分钟 → 2 小时活动可用区间 `[15, 105]` → 30 分钟间隔产出
**4 次**（T+15/45/75/105）。要得到 3 次，留白必须是 **30 分钟**。

**我的取舍**：留白 **30 分钟**，使「2 小时 3 次」成立（验收 A20 可判定）。

**影响面**：
| 活动时长 | 留白 30（当前） | 留白 15 |
|---|---|---|
| 1.5 小时 | 1 次（T+15） | 2 次（T+15/45） |
| 2 小时 | **3 次**（T+15/45/75）✅ | 4 次 |
| 3 小时 | 4 次（T+15/45/75/105） | 5 次 |
| 4 小时 | 6 次 | 7 次 |

**已同步的位置**（改的时候要一起改）：
* `packages/shared_core/lib/src/contract/field_dictionary.dart` → `attendanceLastTaskMargin`
* `packages/shared_core/lib/src/domain/activity.dart` → `plannedAttendanceSlots()`
* `mock_server/src/constants.js` → `ATTENDANCE_LAST_TASK_MARGIN_MIN`
* `mock_server/src/attendance_engine.js` → `planSlots()`
* 测试：`mock_server/test/smoke.js` 的「验收 A20」与「末次抽查为活动收尾留出 30 分钟」

## O-3　「已发布」→「进行中」的自动流转未定义 🟡

§4.4 写「开始：一键（**到点也可自动**）」。

「也可自动」意味着可选，但没说是谁的责任：
* **客户端定时** → 不可靠（iOS 调度不确定、Android Doze、国产 ROM 杀进程，§6.2 已承认这点）；
* **服务端定时** → 可靠，但需要后端有定时任务，且管理端不在线时活动会"自己开始"。

**我的实现**：**只支持显式点「开始」**，不做任何自动流转。

理由：方案在抽查下发通道上已经明确「移动端无法保证固定周期后台执行」，
同一逻辑适用于状态流转。让客户端负责状态流转会直接导致现场状态不一致。

**★ 需要你确认**：是否要服务端定时自动流转？若要，`published` 到点自动变 `ongoing`
是否需要可关闭？

## O-4　三条零成本底线的第二条与导出功能的张力 🟡

README §3.3 底线②：「**日志与崩溃上报不含完整手机号/学号**」。

**我的实现**：把这个底线**扩到了导出件**（CSV 里手机号也是 `138****5678`）。

**问题**：发布者做现场对账时，可能需要完整手机号来联系未到场的志愿者。
一份全是掩码的名单在"打电话催人"这个场景下没用。

**我的取舍**：先按底线②脱敏。但这个决定**可能影响实际可用性**，需要你确认。

**★ 需要你决定**：
* 方案 A：导出保持脱敏（安全优先，对账靠学号+姓名）；
* 方案 B：导出给完整手机号，但那等于底线②在导出路径上失效；
* 方案 C（我的建议）：**导出默认脱敏，管理端可显式勾选"包含完整联系方式"**，
  且该操作计入审计日志（谁在什么时候导出了含完整号码的名单）。

## O-5　`enrolled` 字段语义不明 🟢

§3 把 `enrolled` 列为活动字段，但 §1.3 明确「用户端自助报名」在**范围外**——
名单完全由发布者维护。那 `enrolled`（已报名人数）到底指什么？

**我的取值**：**有效名单人数**（`signupStatus != cancelled` 且未移出）。

**影响**：如果后端认为它等于"名单总行数（含已移出）"，看板数字会对不上。

## O-6　`quota` 的约束对象不明 🟢

用户端无自助报名，所以 `quota` 只在**名单导入**时起作用。

**我的取值**：导入时超出 `quota` 的行**拒绝并报 `30008`**，不允许超员。

**未定义**：发布者手工单个添加时是否也受 `quota` 限制？我的实现是**受限**。

## O-7　被移出名单的人能否重新加入 🟢

§14.1-7 说「保留并标注『已移出（时间）』」，§4.6 说「软删除」。

**未明确**：「移出」是临时措施（可以再加回来）还是终态（永久排除）？

**我的实现**：
* 发布者可以**重新加入**——通过单个添加或再次导入，会复用原记录、清掉移出标记，
  历史签到与考勤记录**保留**；
* 被移出期间**不能签到、不能绑定**（未发生的抽查一并置 `excused`）。

## O-8　抽查时刻已过时志愿者仍能响应 🟡

§6.2 说「响应窗口 5 分钟；超时 `deadline + 2min` 置 `missed`」。

**未明确**：在 `deadline` 与 `deadline + 2min` 这 2 分钟宽限期里，
志愿者点响应应该成功还是失败？

**我的实现**：
* `deadline` 之前 → 正常完成；
* `deadline` ~ `deadline + 2min` → **拒绝**（"该在岗确认已超时，请联系发布者人工补录"），
  但**不立即置 `missed`**，留给服务端在 `+2min` 时统一定案。

理由：宽限期的目的是**区分「人不在」与「通知没到」**（§13-A5），
不是给志愿者多 2 分钟补点。如果把宽限期用来接受响应，这两个概念就又混在一起了。

**★ 需要你确认**：宽限期内是否接受响应？

## O-9　在岗抽查的判定范围未定义 🟡

§6.1 详细定义了**签到**的围栏与评分，但 §6.2 只说了抽查的**时间**参数，
**没说位置判据**——抽查时志愿者该在哪个范围内才算在岗？

**我的实现**：距场地 `max(签到半径 × 2, 500 m)` 以内算完成，超出转人工。

理由：在岗抽查是**防脱岗**，不是入场判定。人在场地边缘走动、在楼下等电梯，
都不该被判脱岗。参照签到半径的 2 倍是保守取值。

**★ 需要你确认**：在岗抽查是否应该用与签到相同的半径？

## O-10　「活动终态 + 7 天」对未签到活动的影响 🟢

§14.1-6 说统一 7 天留存期。§4.4 说取消活动时「未发生的抽查自动 `excused`」。

**未明确**：一个**从未开始就被取消**的活动（没有签到、没有在岗记录），
它的 7 天留存期从取消时刻算，还是从原定结束时刻算？

**我的实现**：从**终态时刻**（取消时刻）算。这符合「活动**终态** + 7 天」的字面表述。

**影响**：若一个活动原定下个月举办，今天取消，那么 7 天后数据销毁——
发布者可能还没意识到活动被取消了。

## O-11　管理端新建活动：坐标设为必填，比方案更严 🟡

**背景**：真机验证需要"在任意地点造一个可签到的活动"，因此补了
管理端的新建活动页（`apps/admin_app/lib/create_activity_page.dart`）。

**方案原文**（§4.1 字段字典）：

| 字段 | 必填 | 校验 |
|---|---|---|
| 活动坐标 `geoLat`/`geoLng` | **否** | WGS-84；**启用围栏时必填** |

**现状**：`ActivityValidator`（A1 阶段写于 shared_core）把坐标当作
**无条件必填**（`lat == null → 请在地图上选择活动位置`）。新建活动页
沿用这个校验，并在界面上明确写"坐标是必填项"。

**为什么保留严格版，而不是立刻放宽**：

1. 这是以签到为核心的平台。一个没有坐标的活动，在真机上表现为
   **所有人签不上**，而界面上完全看不出问题 —— 比创建失败更难排查；
2. 放宽需要改动 shared_core 的校验逻辑与 **154 项测试**，
   而当前阶段（真机验证）没有这个必要。

**代价**：无法创建"线上活动""仅在教室集合但不打卡"这类活动。

**建议的后续**：引入明确的开关（如 `checkinRequired: bool`），
按方案的口径实现「启用围栏时必填」：不启用签到判定的活动允许无坐标，
此时详情页也要显式标注"本活动不做签到判定"。

**需要你确认**：是否认可这个更严格的默认。若你希望严格照方案，
改动点集中在 `validation.dart` 的坐标段与 `create_activity_page.dart` 的提示文案。

## 真机测试（Redmi Note 12T Pro / Android 15）发现的缺陷

> 以下 6 条**全部已修复并有回归测试**，记录在此是因为它们揭示的
> **测试方法问题**比缺陷本身更重要：单元测试全绿，真机一跑就露。
> 详见 `docs/device-test-report.md`。

### O-12　反作弊把"真人站着不动"误判为模拟定位 🔴 → 已修复

**现象**：志愿者站在签到点上不动，3 次采样被服务端判为模拟定位，
得分 `40 + 10 − 60 = −10`，强制转人工。

**根因**：Android 融合定位在设备静止时**直接返回缓存值**，
3 次采样逐位相同（实测 `34.218196 / 117.137571 / ±30m` 三份完全一样）。
原判据只看"完全一致"，于是把老实人当成了作弊。

**连锁后果**：方案 §6.1 的「自动通过」路径实际**永远走不到**；
而且与同一张评分表里的「采样一致 +10」自相矛盾 —— 越一致越像真人，也越像作弊。

**修复**：`detectMockLocation` 中"逐位相同"升级为复合判据 ——
必须同时满足「精度 ≤ 5 m」。真机静态融合定位典型精度 20–50 m，
作弊工具才写 0–5 m。Android 的 `isMock` 权威标志仍单独生效（命中即转人工）。

**回归测试**：`mock_server/test/smoke.js`
`真机站着不动：多次采样逐位相同但精度正常（±30m）→ 不得判为模拟定位`

### O-13　在岗确认接口恒返回 404（整条链路不可用）🔴 → 已修复

**现象**：点「我在现场」永远报「内容不存在 / 活动不存在或已过留存期」。

**根因**：路由是 `/attendances/:taskId:confirm`，参数名是 **`taskId`**，
而 `respondAttendance` 读的是 **`ctx.params.id`** —— 恒为 `undefined`，
`findVisibleActivity(undefined)` 返回 null → 404。

**为什么单测没抓到**：测试**直接调用 handler**，并且手工构造
`params: { id, taskId }` —— 两个参数都塞进去，`ctx.params.id` 在测试里是好的。
这是"直接调 handler 的测试"在参数名层面**永远不可靠**的典型。

**修复**：以 `taskId` 为主键找任务，再由 `task.activityId` 推活动。
`remindAttendance`（催办）同一处错误，一并修复。

**回归测试**：
* `每个处理函数读取的 ctx.params.* 必须在路由模式里声明（防参数名漂移）`
  —— 静态扫描 **全部路由**，把处理函数源码里读的 `ctx.params.X`
  与路由模式声明的参数名比对。这类检查一次覆盖所有接口。
* `在岗确认：以 taskId 为主键解析活动，不再依赖不存在的 ctx.params.id`

### O-14　在岗确认的报文形状与客户端不一致 🟠 → 已修复

**现象**：修好 O-13 后，确认仍失败：「未收到定位证据」。
但定位权限已开、定位也采到了。

**根因**：客户端按契约发**嵌套**结构

```json
{ "method": "geo",
  "location": { "lat": 34.218, "lng": 117.137, "accuracy": 30 },
  "device": { "mockLocationDetected": false } }
```

而 `respondAttendance` 读的是**扁平**的 `ctx.body.geoLat` / `ctx.body.accuracy`。

签到接口早就有 `normalizeCheckinPayload` 处理嵌套，确认接口却各写一套 ——
**同一套定位证据、两个接口、两种报文形状**。

**修复**：确认接口复用同一个归一化函数（`normalizeAttendancePayload`）。

**回归测试**：`在岗确认：接受契约的嵌套 location 报文（而不是只认扁平 geoLat）`

### O-15　可以提前确认未来的在岗抽查（防脱岗失效）🔴 → 已修复

**现象**：活动 13:25 开始，第 3 次抽查计划 **14:40**，
**14:03 点「我在现场」直接变成 `done`**。

**根因**：抽查任务在签到时就把 T+15 / T+45 / T+75 全部预创建好。
服务端只拦了"已过期"，**没拦"还没到点"**。

**后果**：志愿者签到完可以把所有未来的抽查一次性全部点掉，
然后离开场地也不会被查出脱岗 —— **防脱岗抽查完全失效**。

**修复**：只在 `[scheduledAt, deadlineAt]` 内允许确认。
（`deadline` 那侧由 `settleOverdueTasks` 负责，`scheduledAt` 这侧显式校验。）

**修复过程中又踩一个坑**：第一版写成
`Number.isFinite(parseTime(...))` —— `parseTime` 返回的是 **Date 对象**而非毫秒数，
`Number.isFinite` 恒为 false，**守卫被静默跳过**（看起来有校验，实际一次没生效）。
改为 `parseTime(...)?.getTime()`。这个坑正是被新写的测试当场抓到的。

**客户端同步修复**：未开始的任务显示「19:38 后开始」+ **禁用按钮**
（原先显示可点的「我在现场」，点下去必被服务端拒绝，白采集一次定位）。

**回归测试**：
* `在岗确认：未到计划时刻不得提前确认（防脱岗抽查不能被预先点掉）`

**与 O-8 的关系**：O-8 讨论的是 `deadline` **之后**那 2 分钟宽限期；
本条是 `scheduledAt` **之前**完全没有校验，两者是窗口的两侧，都需要显式处理。

### O-16　管理端「用当前位置」与「权限最小化」的冲突 🟠 → 已按功能需要放开，需你确认

**背景**：管理端最初用 `tools:node="remove"` **显式剔除**定位权限，
理由是「管理端只做发布/复核，位置判定的主体是志愿者」（方案 §7）。

**冲突**：后来加了「新建活动 → 用当前位置作为签到点」，
发布者需要在现场把签到点定在自己脚下（方案 §4.1 也把活动坐标的来源标为「管理端」）。

**处理**：删除 `tools:node="remove"`，改为显式声明 `ACCESS_FINE_LOCATION` /
`ACCESS_COARSE_LOCATION`，并在清单注释里写明用途边界：

| 用途 | 用户端 | 管理端 |
|---|---|---|
| 签到/在岗确认的在场证据 | 必需 | 不需要 |
| 录入活动时取一次签到点坐标 | 不用 | **仅此一处** |

**仍然不做**：不申请 `ACCESS_BACKGROUND_LOCATION`；不采集持续轨迹；
不在启动时索取权限（只有真点了那个按钮才请求）。

**真机验证**：首次点「用当前位置」弹出系统权限框（含"精确/模糊"两档，
这正是同时声明 COARSE 的价值），授予后取得 `34.218194, 117.137561 ±30m`。

**★ 需要你确认**：管理端是否认可放开定位权限？
若不认可，替代方案是去掉「用当前位置」按钮、改为纯手工填经纬度 ——
但那会让"在任意地点造活动"变得很麻烦。

### O-17　未配置网络白名单时，签到永远无法自动通过 🟡 → 属设计如此，需知晓

**现象**：单次签到只拿到「围栏 40 + 采样一致 10 = 50」，
低于自动通过门槛 60，稳定落入待人工确认。

**原因**：`SCORE_WIFI_BSSID_MATCHED(+20)` 与 `SCORE_CAMPUS_IP_MATCHED(+10)`
只在**活动配置了 `wifiBssids` / `campusIpPrefixes`** 时才计分
（"无法证明就不参与判定"，这是对的 —— 否则任何人填个 BSSID 都能拿 20 分）。

**真机配置验证**：给活动配上 `campusIpPrefixes: ["10.176."]` 后，
同一台手机同一位置重测 → `40 + 10(校园网) + 10(采样一致) = 60` → **自动通过**。
说明自动通过链路本身是通的。

**遗留影响（需要产品决策）**：

1. 活动必须由发布者**预先配置**网络白名单，否则自动通过不可达；
   而新建活动页目前**没有**这两项的录入入口。
2. 手机当热点时 Wi-Fi 客户端关闭，`getWifiIP()` 返回**蜂窝 IP**，
   `wifiBssid` 为空 —— 真实校园场景（手机连校园 Wi-Fi）才拿得到这两项证据。
3. 因此**待人工确认率可能远高于预期**，这直接影响现场发布者的工作量。

**★ 建议**：在新建活动页补上「场地 Wi-Fi / 校园网前缀」的录入，
并在管理端「待确认」列表里显示每条的评分明细（现有 `scoreBreakdown`
已经能解释"为什么是这个分"，界面需要把它展示出来）。

## 第二轮真机测试（离线 / 复核 / 权限）发现的缺陷

> 这一轮的 5 个缺陷全部已修复并有回归测试。
> 共同点：它们都属于"**界面在承诺一件代码没做的事**"，
> 比直接报错更危险 —— 用户会以为已经交上去了。

### O-18　绑定非幂等：一次网络抖动就永久锁死 🔴 → 已修复

**现象**：首次绑定因网络抖动**超时**，界面显示「网络超时」。
用户重试 → 「该邀请码已被使用」→ **再也绑不上**，只能找发布者重新发码。

**根因**：服务端其实**已经绑定成功**（邀请码消费、grant 签发、名单绑定全部落库），
只是响应没送达客户端。而邀请码是"用后即失效"的一次性凭证，
重试时服务端只看 `invite.usedAt` 就拒绝。

**修复**：邀请码已被使用时，先判断是不是**同一设备 + 同一学号**在用：

* 是 → 幂等返回既有 grant（`idempotentReplay: true`），令牌不变；
* 否（码被别人用了）→ 仍然拒绝，一次性语义不变。

安全上等价：`deviceId` 本身就是绑定凭据，能复现它说明还是同一台机器。

**回归测试**：`同一设备重试绑定 → 幂等返回原授权，而不是「邀请码已被使用」`
（已有测试 `一次性邀请码用过即失效` 用不同 deviceId 验证反向仍会被拒。）

### O-19　离线队列根本没落盘：「已保存到本机」是假的 🔴 → 已修复

**现象**：离线签到时界面明确写「**已保存到本机**」。
但 App 被划掉（或 Android 回收进程）后，证据凭空消失，
而用户以为自己已经交上去了 —— 直到事后被判定缺席才发现。

**根因**：`OfflineQueue` 一直是**纯内存**的。
`persist()` / `restore()` 两个方法都实现了，但**宿主从来没调用过**。
`user_app` 也没有任何普通本地存储依赖（只有令牌走 `flutter_secure_storage`）。

**修复**：

1. `OfflineQueue` 增加 `onChanged` 回调，在入队 / 移除 / 清空 / 补传后**自动通知宿主**。
   （与其在每个调用点手写 `persist()`——漏一处就静默丢数据——不如让队列自己通知。）
2. 新增 `shared_platform/src/queue_store.dart`：用 `path_provider` 把队列 JSON
   写到应用私有目录，**先写 `.tmp` 再 rename**（同目录 rename 原子，
   避免写到一半被杀留下半个 JSON）。
3. `bootstrap` 里接线 `queue.onChanged = () => queueStore.save(queue.persist())`；
   `main._restoreAuth` 在进主页前 `queue.restore(load())`。

**真机验证**：离线签到 → 界面「已保存到本机」→ `am force-stop` 杀进程 →
重启服务器 → 重新打开 App → **服务端出现该记录，`offlineBackfill=true`**。

**回归测试**：`任何队列变更都要触发 onChanged（宿主据此落盘）`、
`persist → restore 往返后队列内容一致`

---

### O-20　「联网后自动上传」从来没有实现 🟠 → 已修复

**现象**：离线入队的提示写着「**联网后自动上传**」，
但实际上 `queue.flush()` **只在「我的记录 → 立即重试」里被调用** ——
没有任何自动触发点。用户不进记录页点按钮，证据就永远躺在本机。

**根因**：功能只写了一半点。提示文案先落地了，自动触发没做。

**修复**：`_ActivityList` 增加 `_autoFlushQueue()`，两个触发时机：

1. 进入主页（= 打开 App 且已有授权）—— 最典型的"刚才没网，现在有网了"；
2. 点右上角刷新之后 —— 用户主动确认网络可用，补传成功率最高。

失败**静默**（补传是尽力而为，弹错误只会打扰用户），
「记录」页的角标与「立即重试」仍是兜底入口。

### O-21　跨发布者越权：管理员能看到所有人的活动 🔴 → 已修复

**现象**：用只发过 0 条活动的管理员账号登录管理端，
工作台却列出了 **6 条属于另一个发布者的活动**（界面写的是「我发布的」）。
且点进「现场看板」报 `40301 无权操作该活动` —— 列表能看、操作不能，
自相矛盾暴露了问题。

**根因**：`route('GET', '/activities', api.listActivities)` **没有 `auth` 选项**，
于是 `authenticate` 从不执行、`ctx.auth` 一直是空对象 `{}`，
`listActivities` 里 `ctx.auth.kind === 'admin'` 恒为 false，
走的是"非管理员"分支（仅排除草稿）——**归属过滤整段失效**。

**修复**：新增 `optional` 鉴权模式 —— 有令牌就解析，没令牌就当匿名。
`GET /activities` 改用它：网页端匿名浏览公开列表照常可用，
管理端带令牌则按 `ownerId` 过滤。

**真机验证**：修复后工作台「我发布的活动 共 1 个」只剩自己建的那条；
匿名请求仍能拿到 6 条公开活动（网页端不受影响）。

**回归测试**：
* `活动列表：管理员只能看到自己名下的活动（归属隔离）`
* `活动列表：匿名请求仍可浏览公开活动（网页端不能被迫登录）`
* `GET /activities 与 GET /changes 必须声明 optional 鉴权`（静态守卫）

### O-23　e2e 测试会污染正在运行的 mock 数据（测试卫生）🟡

`shared_core` 里的 e2e 测试（`e2e_admin_flows_test.dart` 等）
**连接到"已经在 8080 上运行的任意 mock server"**，没有就整体跳过。

后果：一边开真机测试服务器、一边跑 `flutter test`，
e2e 会把「A2 端到端活动」这类数据写进**真机测试用的库**。
本次实测因此出现过「我发布的活动 共 27 个」的污染现场。

**建议**：给 mock server 加一个 `MOCK_E2E=1` 标记，
e2e 测试只对带该标记的实例执行；或在文档里明确"跑 e2e 前先关掉真机服务器"。
